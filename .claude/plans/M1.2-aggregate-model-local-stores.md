## Goal (scope of THIS task only)

Turn three of the six seams from M1.1 skeletons into **working local adapters**, and encode the **aggregate model** as Bridge-core code:

1. **Aggregate model as code** (`bridge/src/bridge/aggregate.py`): the exchange/task/session/party bindings and the **exchange-as-view-over-tasks** read path (ADR-0003), with a **deterministic sort key baked in from day one** (A5).
2. **Exchange store local adapter** (`LocalExchangeStore`): real in-memory behavior — view-by-default, one-way `materialize`, keyed on the A2A `context_id` (never a new id).
3. **Sessions + Task store local adapters that survive a process restart**: reconcile M1.1's `InMemory*` factory wiring with M1.2's explicit "task store survives restart" requirement by adding a **durable local variant** (`sqlite+aiosqlite`) alongside the in-memory default, and prove restart with a test — porting the S1-6 recipe into `bridge/`.

This is the aggregate + storage foundation. It does **not** build the ledger projection (M1.4), the A2A server edge (M1.8), disposition (M1.6), or the scheduler (M1.12).

### Explicitly NOT in this task
- **No classified-ledger projection** — M1.4. The exchange view here exposes its ordered tasks and a hook for the ledger; the `LedgerEntry` fold is M1.4.
- **No A2A server / message handling** — M1.8. M1.2 provides the aggregate helpers M1.8 will call to mint a context, create a task-per-leg, and read the view; it does not stand up a JSON-RPC server.
- **No disposition / classification / issuer canonicalization** — M1.5/M1.6.
- **No scheduler timers** — M1.12 (leave `LocalScheduler` skeleton untouched).
- **No skill registry behavior** — M1.3 (leave `LocalSkillRegistry` skeleton untouched).
- **No GCP adapters** — Sprint 2. The `gcp` fixture branch keeps skipping. "Durable local" (`sqlite`) is still a **local** adapter, not the GCP one.
- **No exchange materialization *trigger*** wired into a real flow — Phase 2/3 (program membership / Requirements artifact / reopen). M1.2 only implements the `materialize()` mechanism + its one-way guarantee so it is testable; nothing in Phase-1 Address calls it (ADR-0003: Address stays view-only).

## Design decisions (made here — do not re-litigate)

- **D1 — Aggregate model lives in a new pure-ish module `bridge/src/bridge/aggregate.py`.** It holds: context minting, the task↔session 1:1 binding convention, the deterministic-ordinal stamp, and `build_exchange_view(...)`. It imports `contract` + `a2a.types` only (never `agents`). Keep `bridge/src/bridge/__init__.py` minimal (do not import `aggregate`/seams from it — preserve the cheap `import bridge` and the no-agents guard's clarity).
- **D2 — Exchange identity IS the A2A `context_id`; there is no separate exchange id.** `mint_context_id()` returns a fresh id at request time (recommend `f"ctx-{uuid4().hex}"`). Materialization must reuse the same `context_id` — never mint a new one (ADR-0003 consequence; `wiki/bridge-aggregate-model.md`).
- **D3 — The exchange view groups tasks by their `context_id` field; the caller supplies the candidate tasks.** `build_exchange_view(context_id: str, tasks: Iterable[Task]) -> ExchangeView` filters `tasks` to those whose `.context_id == context_id` and sorts them by the deterministic key (D4). This **sidesteps the proto `TaskStore.list` awkwardness** (proto `ListTasksRequest` + `ServerCallContext`): M1.2's view is unit-testable from an explicit task list, and M1.8 (the A2A edge, which already holds a `ServerCallContext`) will feed it the tasks it fetched. Also provide a thin `async tasks_for_context(task_store, context_id, *, call_context) -> list[Task]` helper that wraps whatever the real `list` call is — but **the implementer verifies the exact proto call at build time**; if it proves fiddly, ship `build_exchange_view` (explicit tasks) as the primary API and leave `tasks_for_context` as a best-effort convenience with a `# M1.8 wires the real list call` note. The view path (not the store-list plumbing) is the M1.2 deliverable.
- **D4 — Deterministic sort key = an explicit per-context ordinal stamped into `task.metadata` at creation (A5).** A2A `Task` has no timestamp; in-memory rides dict insertion order but `DatabaseTaskStore`/relational returns rows unordered. So at task creation the aggregate stamps `task.metadata["bridge_ordinal"] = <n>` where `n` = the count of tasks already in that context (0-based). `build_exchange_view` sorts by that ordinal. It is **durable** (persisted on the task row, survives restart) and **backend-independent** — this is the concrete answer to A5. Provide `create_leg_task(context_id, ordinal, ...) -> Task` (or `stamp_ordinal(task, ordinal)`) in the aggregate. Document that chronological order beyond this ordinal is *not* guaranteed and needs no extra state. (Fallback if metadata-stamping on the proto Struct proves painful: sort by `task.id` — deterministic but not creation-ordered — and record the compromise in the module docstring. Prefer the ordinal.)
- **D5 — Task ≈ session, 1:1, keyed identically.** Convention: `session_id == task_id`. The aggregate exposes this as a named constant/helper (e.g. `session_id_for_task(task_id) -> str` returning the same string) so the 1:1 binding is explicit and greppable, matching `wiki/bridge-aggregate-model.md` ("one task is one runtime session, keyed one-to-one"). No wrapper class needed.
- **D6 — Party is a plain stable reference string, NOT an aggregate.** No `Party` model, no store. It rides on `CollectRequest.party` and (per the aggregate model) scopes a task's counterparty reference, falling back to the exchange context when none is supplied. Encode as a small helper `party_scope(request) -> str` returning `request.party or context_id`; do **not** build a party store/entity (`wiki/bridge-aggregate-model.md`: "Party is not an aggregate").
- **D7 — `LocalExchangeStore` implements ADR-0003 view-by-default semantics:**
  - `get(context_id) -> ExchangeRecord | None`: returns `None` for an unmaterialized exchange (the caller then uses `build_exchange_view` over tasks). Only materialized exchanges have a stored record.
  - `save(record)`: upserts a materialized record keyed by `record.context_id`.
  - `materialize(context_id, **kwargs) -> ExchangeRecord`: **one-way** — first call creates + stores the record; if already materialized, return the existing record (idempotent) **without** overwriting exchange-only state (or raise a clear error on conflicting init — pick idempotent-return and document it). Never mint a new id.
  - Backing = an in-memory `dict[str, ExchangeRecord]` (this adapter is the local one; the GCP relational adapter is Sprint 2). Deterministic iteration if it ever lists (dict insertion order is fine in-memory; note A5 applies to the *persistent* adapter).
- **D8 — Define a minimal `ExchangeRecord` type (the "concrete exchange record type" the M1.1 Protocol deferred to M1.2).** A small `pydantic.BaseModel` (or frozen dataclass) in `aggregate.py`: at least `context_id: str`, `materialized: bool = True`, and an open `state: dict` for the exchange-only state that forces materialization later (Requirements artifact / program membership / skill binding / reopen). Keep it minimal — do **not** pre-model Requirements/program aggregates (those are Phase 2/3). Tighten the `ExchangeStoreSeam` signatures in `seams/exchange_store.py` from `object` to `ExchangeRecord` where it reads cleanly (optional; runtime_checkable won't break either way — but do not create an import cycle: the seam module may import `ExchangeRecord` from `aggregate` **only if** `aggregate` doesn't import the seam; if that risks a cycle, leave the Protocol as `object` and just document the concrete type). Prefer: keep the seam Protocol on `object`, define `ExchangeRecord` in `aggregate.py`, have `LocalExchangeStore` use it concretely.
- **D9 — Durable local variant via a factory flag, not a new seam.** Extend `build_local_adapter(seam, *, durable: bool = False, db_path: str | None = None)`. `durable=False` keeps M1.1 behavior (`InMemorySessionService`/`InMemoryTaskStore`). `durable=True` returns `DatabaseSessionService(db_url=f"sqlite+aiosqlite:///{db_path}")` and `DatabaseTaskStore(engine=create_async_engine(f"sqlite+aiosqlite:///{db_path}"), create_table=True)` (only meaningful for `SESSIONS`/`TASK_STORE`; for the other seams `durable` is ignored). This keeps the "swap is a no-op for the agent" idiom: same seam, same Protocol, storage swapped. Keep the existing `build_local_adapter(seam)` call sites working (default arg). Add the C3 env-hook comment already present.

## Gotchas (ordered by how likely they are to bite)
1. **`a2a.types.Task` is protobuf, not pydantic** — no `model_fields`; construct keyword-style; `metadata` is a `google.protobuf.Struct` (set it like a dict; read back may need `dict(task.metadata)` or field access). Verify the exact ordinal set/read on the Struct before building the view sort.
2. **`TaskStore.save/get/list` require a `ServerCallContext`** and `list` takes a proto `ListTasksRequest` returning `ListTasksResponse` — not the simple signatures the M1.1 Protocol shows (Protocol conforms by name only). Design the M1.2 view around an **explicit task list** (D3) so unit tests don't need the proto/context; only `test_local_stores_durable.py` touches the real `save/get`, where you must synthesize/obtain a `ServerCallContext` (check `a2a.server.context` and how the mock/handler builds one).
3. **`sqlite+aiosqlite:///` (async driver), not `sqlite:///`** — the S1-6-locked deviation; bare `sqlite://` fails under `DatabaseSessionService`. Also **close/flush store #1** before reopening the file, or the restart read races the write.
4. **Missing deps** — `DatabaseSessionService` import fails today (no `sqlalchemy` in `bridge/`); Step 1's `google-adk[db]` + `a2a-sdk[http-server,sql]` + `aiosqlite` + re-lock is a hard prerequisite for the durable tests. Do Step 1 first.
5. **The exchange-store deferral test WILL break.** `test_exchange_store_skeleton_defers` asserts `NotImplementedError` — remove it when `LocalExchangeStore` gains real behavior, or the suite goes red. Leave the skill_registry/scheduler/extraction deferral tests alone (still skeletons).
6. **`materialize` is one-way (ADR-0003).** Do not let a second `materialize`/`save` silently clobber exchange-only state or mint a new id. Idempotent-return on re-materialize; keep `context_id` stable throughout.
7. **No import cycle** `aggregate` ↔ `seams`/`adapters`. Direction is adapters → aggregate (fine); aggregate imports only `contract`/`a2a`. Keep `bridge/__init__.py` from importing `aggregate`/seams so `import bridge` stays cheap and the no-agents guard stays meaningful.
8. **Don't build the ledger fold here** — that's M1.4. The view exposes ordered tasks + a documented hook; resist folding `LedgerEntry` now.
9. **Party is not an aggregate** — resist adding a `Party` model/store; it's a plain reference string (D6).
