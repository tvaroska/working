# M1.10 — A2UI edge (content-not-pixels human surface)

**Milestone:** M1 — Bridge Core (local) · **Depends on:** M1.7 (`bridge/fulfillment.py` Path-B graph), M1.9 (`bridge/requirements.py` — advisory + `RequirementsList` + verbatim relay) · **Blocks:** M1.11 (dual-path routing dispatches Path B *here*), Frontend v1 (hosts this) · **Design roots:** `wiki/bridge-a2ui-edge.md`, `wiki/bridge-dual-path.md`, `wiki/bridge-frontend.md`, `wiki/bridge-edges.md`

## 1. Goal (what "done" means)

Build the Bridge's **human-facing edge** as a new bridge-local edge package `bridge/src/bridge/edges/a2ui/`, giving it four capabilities (the four verbs in the task line):

1. **Emit "what to show / what comes back"** — declarative, content-not-pixels view/intake models (Pydantic, JSON-serializable). The Bridge describes *what* to collect (upload a file / paste text / fill a form) and *what structured response* it expects back; never *how it looks* (`wiki/bridge-a2ui-edge.md`).
2. **Ingest the structured response** — an `A2uiResponse` model + a mapper turning it into a Path-B intake document.
3. **Feed Path-B intake into the extraction graph (M1.7)** — the mapped intake is passed to `bridge.fulfillment.run_fulfillment(...)` (the deterministic Path-B graph); resubmission `attempts` thread forward.
4. **Render the party-status view ("sent / accepted / outstanding / next")** — a pure projection over `CollectionStatus` (the classified ledger, M1.4) + `RequirementsList` (M1.9), plus a **reference text renderer** explicitly marked demo furniture ("not the product").

**Single hard acceptance:** given the 8 eval fixtures fed as A2UI Path-B intake, `submit_intake` reaches the same `FulfillmentResult` phase/disposition as M1.7's `run_fulfillment` (proving the A2UI edge feeds the graph); and `party_status_view` buckets a mixed ledger + requirements correctly with the M1.9 `message` relayed **verbatim**.

### Non-goals (do NOT do here)
- **No React/frontend work.** Frontend v1 (separate, unchecked Sprint-1 task) hosts this; the reference renderer here is a Python text renderer = demo furniture. Do not touch `frontend/`.
- **No dual-path routing / dispatch.** Deciding Path A (A2A) vs Path B (A2UI) by the arriving Part is **M1.11**. M1.10 only *provides* the A2UI intake handler that M1.11 will dispatch to.
- **No HTTP server / Starlette app for A2UI.** Unlike the A2A edge (M1.8, JSON-RPC over HTTP because A2A mandates it), the A2UI edge is a Python edge module (models + projection + intake feed + renderer). The frontend host (later) owns transport. Keep it a library surface; do not stand up a web server.
- **No requirements computation.** `RequirementsList`/`CollectionStatus` are *inputs* to the projection — computed by M1.9 (`propose_requirements`). M1.10 renders them; it does not recompute the satisfaction rule.
- **No real upload/blob handling or Gemini.** Local uses the fixture engine (ADR-0005); an A2UI response carries a `fixture_id` (demo furniture) that maps to `FixtureDocument`. Real blob→Gemini is Sprint 2 / Phase 4.
- **No HITL-review or dashboard surface.** `wiki/bridge-a2ui-edge.md` lists HITL review / internal dashboard as *other* surfaces on this edge; M1.10 scope is the **party-status + Path-B intake** surface only (the end-user/provider portal). Note the others as future.

## 2. Key design decisions & gotchas (read before coding)

- **A2UI view models are bridge-local, NOT in `contract`.** `contract/` holds the **agent↔Bridge A2A** shapes (`CollectRequest`, `ExchangeTurn`, `CollectionStatus`, `RequirementsList`). The A2UI declarative shapes are the **human-edge rendering protocol** between the Bridge and any host renderer — analogous to how the A2A edge keeps `plan.py`/`trust.py`/executor bridge-local rather than in `contract`. The frontend is TypeScript and consumes JSON, not the Python types, so there is no cross-language sharing pressure. Put them in `bridge/edges/a2ui/views.py`. State this rationale in the module docstring so nobody "promotes" them to `contract`.
- **The projection consumes contract types.** `party_status_view` takes `CollectionStatus` (ledger) + `RequirementsList` (M1.9) — both `contract` types — and emits bridge-local view models that *embed the relayed prose*. The `message` on rejected `LedgerEntry`s and on `Requirement`s is relayed **verbatim** (ADR-0013); M1.10 must not author or edit prose — only bucket/forward it.
- **`sent`/`accepted` come from the ledger; `outstanding`/`next` come from requirements.** Concretely:
  - `sent` = every `LedgerEntry` in `status.ledger`.
  - `accepted` = entries with `disposition == ACCEPTED`.
  - `outstanding` = `[req.item for req in requirements.requirements if req.status == RequirementStatus.REQUIRED]`.
  - `next` = the first REQUIRED requirement's `message` (verbatim), or `None` when `requirements.done`.
  - `done` = `requirements.done`.
  Do **not** derive `done` from `CollectionStatus.terminal` — `done` is the app-owned completeness (M1.9 `RequirementsList.done`); `terminal` is the exchange-lifecycle flag. Keep them distinct (M1.9 §2 gotcha).
- **Intake is a Path-B document.** Local: the `A2uiResponse` carries a `fixture_id` → `FixtureDocument(fixture_id=...)` (the same value object M1.7's fixture engine and `executor.py` already use). Missing `fixture_id` in upload mode → raise `ValueError` (the local fixture engine needs a fixture id; document that real blob intake is Sprint-2/Phase-4). An inline `extraction` passthrough is optional (the fixture engine already supports `FixtureDocument(extraction=...)`).
- **Thread `attempts` for the resubmission loop.** `submit_intake` must accept an `attempts` arg and pass it to `run_fulfillment` (M1.7 threads resubmissions by the caller carrying `attempts=prior.attempts`). This is how the A2UI resubmission loop (upload a clearer copy) reaches escalation after 3.
- **Import discipline (edges → core/seams/adapters; never `agents`).** `bridge/edges/a2ui/` may import `contract`, `bridge.fulfillment`, `bridge.requirements`, `bridge.seams.extraction` (`ExtractionSeam`), and `bridge.adapters.local.extraction` (`FixtureDocument`) — edges are allowed to touch adapters (see `bridge/src/bridge/edges/__init__.py` docstring; the A2A edge already imports `bridge.adapters.local.*`). It must **never** import `agents`. Keep the new modules **out of `bridge/__init__.py`** (same rule every non-`__init__` bridge module follows — preserve cheap `import bridge` + the no-agents guard clarity).
- **Reference renderer is demo furniture.** `render_screen(...) -> str` returns a plain-text rendering. Its docstring must say it is a reference/demo renderer, **not the product** (`wiki/bridge-a2ui-edge.md`: "The project ships a reference renderer as demo furniture — it is not the product.").
- **Keep everything pure/deterministic except `submit_intake`.** The projection and renderer are pure sync functions; only `submit_intake` is `async` (it awaits the extraction seam via `run_fulfillment`). Matches the bridge idiom (pure core + async only where the seam is touched).

## 3. Files to create

### 1. `bridge/src/bridge/edges/a2ui/__init__.py` (new)
Package docstring: the A2UI edge is the human-facing, content-not-pixels surface (`wiki/bridge-a2ui-edge.md`); it renders the party-status view from ledger + requirements (M1.9) and feeds Path-B intake into the fulfillment graph (M1.7); the view models are bridge-local (not `contract`); reference renderer is demo furniture; imports no `agents`; kept out of `bridge/__init__.py`. Re-export the public API:
`build_screen`, `party_status_view`, `PartyStatusView`, `DocStatus`, `IntakeSpec`, `ResponseField`, `A2uiScreen`, `A2uiResponse`, `IntakeMode`, `intake_to_document`, `submit_intake`, `render_screen`.

### 2. `bridge/src/bridge/edges/a2ui/views.py` (new) — declarative view models + projection
- `class DocStatus(BaseModel, frozen=True)` (`extra="forbid"`): `id: str`, `doctype: str`, `issuer: str | None = None`, `disposition: Disposition`, `message: str | None = None` (verbatim relay from the ledger entry for rejected docs).
- `class ResponseField(BaseModel, frozen=True)`: `key: str`, `label: str`, `input: Literal["file", "text", "form"]`, `required: bool = True`. ("What comes back" — a declarative affordance, content-not-pixels.)
- `class IntakeSpec(BaseModel, frozen=True)`: `prompt: str` (the next-action prose, verbatim from the requirement `message`), `doctype_hint: str | None = None`, `accepts: list[ResponseField]`. ("What to show.")
- `class PartyStatusView(BaseModel, frozen=True)`: `sent: list[DocStatus]`, `accepted: list[DocStatus]`, `outstanding: list[str]`, `next: str | None`, `done: bool`.
- `class A2uiScreen(BaseModel, frozen=True)`: `status: PartyStatusView`, `intake: IntakeSpec | None` (None when `done`).
- `def party_status_view(status: CollectionStatus, requirements: RequirementsList) -> PartyStatusView` — the pure projection (buckets per §2). Map each `LedgerEntry` → `DocStatus` (carry `message` verbatim). `next` = first REQUIRED requirement's `message` (or None if done).
- `def build_screen(status: CollectionStatus, requirements: RequirementsList) -> A2uiScreen` — compose the view + intake spec. Intake spec is `None` when `requirements.done`; otherwise built from the first REQUIRED requirement: `prompt = req.message or ""`, `doctype_hint = req.doctype_hint`, `accepts = [ResponseField(key="document", label="Upload a document", input="file"), ResponseField(key="text", label="Or paste the details", input="text", required=False)]`. Keep the affordance list a small static default (content, not pixels).
- `__all__` for the above. Imports: `contract` (`CollectionStatus`, `RequirementsList`, `Disposition`, `RequirementStatus`, `LedgerEntry`) + pydantic + `typing.Literal`.

### 3. `bridge/src/bridge/edges/a2ui/intake.py` (new) — ingest + feed the graph
- `class IntakeMode(StrEnum)`: `UPLOAD = "upload"`, `TEXT = "text"`, `FORM = "form"`.
- `class A2uiResponse(BaseModel, frozen=True)` (`extra="forbid"`): `mode: IntakeMode = IntakeMode.UPLOAD`, `fixture_id: str | None = None` (local/demo: which fixture doc arrived), `text: str | None = None`, `fields: dict[str, str] = {}`. Docstring: the structured response a host renderer sends back; in Phase-1 local, `fixture_id` selects a deterministic eval fixture (demo furniture) — real blob/text→Gemini intake is Sprint-2/Phase-4.
- `def intake_to_document(response: A2uiResponse) -> FixtureDocument` — map the response to a Path-B intake:
  - if `response.fixture_id`: return `FixtureDocument(fixture_id=response.fixture_id)`.
  - else: `raise ValueError("A2UI intake requires a fixture_id in Phase-1 local (real blob intake is Sprint-2/Phase-4)")`.
- `async def submit_intake(response: A2uiResponse, *, engine: ExtractionSeam, thresholds: DispositionThresholds | None = None, max_resubmissions: int = 3, attempts: int = 0) -> FulfillmentResult` — feed Path-B intake into the M1.7 graph:
  - `document = intake_to_document(response)`
  - `return await run_fulfillment(document, engine=engine, thresholds=thresholds or DispositionThresholds(), max_resubmissions=max_resubmissions, attempts=attempts)`.
  - Docstring: resubmission threads `attempts` forward (caller passes `attempts=prior.attempts` on a resubmitted upload — the non-resumable resubmit loop, A1).
- `__all__` for the above. Imports: `contract` (none needed beyond what run_fulfillment returns), `bridge.fulfillment` (`run_fulfillment`, `FulfillmentResult`), `bridge.seams.extraction` (`ExtractionSeam`), `bridge.adapters.local.extraction` (`FixtureDocument`), `bridge.skills` (`DispositionThresholds`), stdlib `enum`.

### 4. `bridge/src/bridge/edges/a2ui/renderer.py` (new) — reference renderer (demo furniture)
- `def render_screen(screen: A2uiScreen) -> str` — a plain-text rendering of the declarative screen: a "Sent:" list (id + disposition, plus verbatim `message` for rejected), an "Accepted:" summary, an "Outstanding:" list, a "Next:" line (the verbatim prompt), and "Done." when `screen.status.done`. Keep it small.
- Module + function docstring: **reference/demo renderer, not the product** — proves the content-not-pixels contract without a real frontend (`wiki/bridge-a2ui-edge.md`). Any host renders the same `A2uiScreen` in its own design system.
- `__all__ = ["render_screen"]`. Imports: `.views` only.

## 6. Acceptance criteria (all must hold)
1. `submit_intake` reaches the **same** `FulfillmentResult` (phase/disposition/flags) as M1.7's `run_fulfillment` for every eval fixture — the A2UI edge feeds Path-B intake into the extraction graph (M1.7), threading `attempts` for the resubmission loop.
2. `party_status_view` buckets a mixed ledger + requirements into `sent`/`accepted`/`outstanding`/`next`/`done` correctly, with per-doc and next-action `message` prose **relayed verbatim** from M1.9 (Bridge authors/edits nothing — ADR-0013).
3. `build_screen` emits a declarative, content-not-pixels `A2uiScreen` (status + intake affordances describing what comes back); `intake is None` exactly when `requirements.done`. Screen is JSON-serializable.
4. `render_screen` is a working reference/text renderer, documented as demo furniture (not the product).
5. A2UI view models live in `bridge/edges/a2ui/` (not `contract`); the new modules are absent from `bridge/__init__.py`; `bridge/` imports no `agents/` (`test_no_agents_import.py` green).
6. Full suite green: `cd bridge && uv run ruff check . && uv run pytest` (and `agents/` unchanged). Fall back to `.venv/bin/pytest` if uv is unavailable.
