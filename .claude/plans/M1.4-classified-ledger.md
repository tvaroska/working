# M1.4 — Classified ledger (projection over exchange tasks)

**Milestone:** 1 (Bridge Core, local) · **Task line:** `PLAN.md` M1.4 · **Depends on:** M1.2 (aggregate model + local stores — done: `bridge/src/bridge/aggregate.py`, `ExchangeView`, `build_exchange_view`, the `bridge_ordinal` A5 sort key). **Foundation for:** M1.6 (disposition *records* each doc into the ledger), M1.8 (A2A edge *emits* the projection inside `ExchangeTurn`), M1.9 (advisory `outstanding`/completeness), M1.13 (mock→real terminal-outcome parity).

**Governing refs:** ADR-0003 (exchange = *view over tasks*; the Phase-1 classified ledger is "an append-only view over exchange tasks: doctype, key fields, disposition"; **no standalone stored record** for Address). `docs/lessons-learned.md` **A5** (the ledger has **no timestamp** → the projection needs a **deterministic sort key**; "the ledger is a **view, not a record**"). `wiki/bridge-aggregate-model.md` ("its bounded Collect keeps only a **classified ledger** of accepted docs, which can be derived as a view over the exchange's tasks — **one doc per task**"). `wiki/bridge-artifacts.md` (the classified-ledger entry is *"a metadata payload attached to a task"* — the A2A/aggregate artifact, distinct from the document bytes). `wiki/bridge-collect.md` (sense-A/sense-B split: the **Bridge owns `CollectionStatus`** = "what we have"; the **app owns `RequirementsList` + the final `done`**).

## Goal (scope of THIS task only)

Build the Bridge-core **classified-ledger projection**: a **pure fold** over an exchange's tasks (one doc per task) that produces `list[LedgerEntry]`, deterministically ordered by the M1.2 `bridge_ordinal` sort key, and assembles it into the shipped `CollectionStatus` / `ExchangeTurn` shapes (from the shared `contract` package). It is a **view, not a record** (ADR-0003) — nothing is stored; the projection is recomputed from tasks on every read.

Concretely, THIS task delivers:
1. A **carry convention** for the per-task classified entry: how one `LedgerEntry` rides on one A2A `Task` (durably, backend-independently — parity with the M1.2 ordinal), plus `stamp_ledger_entry` / `ledger_entry_of` helpers.
2. The **deterministic fold** `project_ledger(view) -> list[LedgerEntry]` (ordered by `ordinal_of`, filtered to the context — reuses `build_exchange_view`).
3. The **container assembly** `project_collection_status(...)` / `build_exchange_turn(...)` producing `CollectionStatus` / `ExchangeTurn` — with `outstanding` and `terminal` as **caller-supplied inputs** (they are *not* computed here — see D3).

### Explicitly NOT in this task
- **No disposition / classification / issuer canonicalization** — M1.6. M1.4 *reads* a `LedgerEntry` off a task; M1.6 is what *writes* it (calling `stamp_ledger_entry`). M1.4 ships the read + the helper so M1.6 has a home; it does **not** decide any disposition.
- **No completeness / advisory `outstanding` computation** — M1.9. `outstanding` and `terminal` are **owned by the app/skill rule** (sense B) and by disposition (sense A), not by the projection. M1.4 carries them as passthrough fields (D3). Do **not** import or re-implement `agents/.../satisfaction.py`.
- **No A2A server / wire emission** — M1.8. M1.8 fetches the context's tasks (holding its live `ServerCallContext`) and calls this projection, then emits the `ExchangeTurn`. M1.4 is unit-testable from an explicit task list (same idiom as M1.2's `build_exchange_view`).
- **No exchange materialization / stored `ExchangeRecord`** — Address stays view-only (ADR-0003). Leave `LocalExchangeStore` untouched.
- **No GCP adapters** — Sprint 2.

## Design decisions (made here — do not re-litigate)

- **D1 — New pure module `bridge/src/bridge/ledger.py`.** Holds the carry helpers + the fold + the container assembly. Imports `contract` + `a2a.types` + `bridge.aggregate` (dependency direction `ledger → aggregate` is fine; `aggregate` must **not** import `ledger`). Never imports `agents`, `seams`, or `adapters`. Keep it out of `bridge/__init__.py` (preserve cheap `import bridge` + the no-agents-guard clarity, same rule M1.2 followed for `aggregate`).
- **D2 — One `LedgerEntry` rides on one `Task` as a JSON string in `task.metadata`** under a new key `LEDGER_ENTRY_KEY = "bridge_ledger_entry"`. Write: `task.metadata[LEDGER_ENTRY_KEY] = entry.model_dump_json()`. Read: `LedgerEntry.model_validate_json(task.metadata[LEDGER_ENTRY_KEY])`. Rationale: (a) **durable + backend-independent**, exactly like the M1.2 ordinal — it survives the `DatabaseTaskStore` restart and needs no separate store, honoring "view, not record" (A5); (b) a JSON *string* scalar avoids the fragile protobuf-`Struct` nested-dict path (verified working); (c) it keeps M1.4 storage-agnostic — the *wire* representation (an A2A artifact `DataPart`, `wiki/bridge-artifacts.md`) is **M1.8's** concern and reads the same `LedgerEntry`. If a future task prefers the entry as a first-class A2A artifact, only these two helpers change. Provide `ledger_entry_of(task) -> LedgerEntry | None` (returns `None` for a task with no stamped entry — e.g. an in-flight leg before disposition) and `stamp_ledger_entry(task, entry) -> None`.
- **D3 — `outstanding` and `terminal` are caller-supplied inputs, NOT computed by M1.4.** The sense-A/sense-B split (ADR-0003, `wiki/bridge-collect.md`) makes `outstanding` an **advisory** the skill rule proposes (M1.9) and `terminal` an outcome of disposition + the app's `done` — a model/projection **may never mint completeness** (lessons A3). M1.4 depends only on M1.2 and must be callable *before* M1.6/M1.9 exist, so the projection **carries** these fields through rather than deciding them. Signature: `project_collection_status(view, *, outstanding: Iterable[str] = (), terminal: bool = False) -> CollectionStatus`. Document in the docstring that M1.6 supplies per-doc disposition (already baked into each entry), M1.9 supplies the advisory `outstanding`, and the app owns the final `done`. Do **not** derive `terminal` from task states here (that presumes completeness).
- **D4 — The fold is deterministic by the M1.2 ordinal, not insertion order (A5).** `project_ledger(view: ExchangeView) -> list[LedgerEntry]` iterates `view.tasks` (already ordinal-sorted by `build_exchange_view`) and collects `ledger_entry_of(t)` for each task that **has** an entry (skip `None` — in-flight legs without a disposition yet). Because `view.tasks` is pre-sorted by `ordinal_of`, the ledger order is deterministic regardless of the order tasks were fetched from a relational/GCP store — this is the concrete A5 answer for the *ledger* (M1.2 answered it for the *view*). Provide an overload/convenience that also accepts raw `(context_id, tasks)` and builds the view internally, so callers needn't pre-build it.
- **D5 — Name the top-level assembler `build_exchange_turn` for parity with the mock.** `build_exchange_turn(context_id, tasks, *, outstanding=(), terminal=False) -> ExchangeTurn` mirrors `mock_bridge/fixtures.build_exchange_turn`'s output shape (context-level `ExchangeTurn{context_id, status}`), so M1.13's mock→real swap compares like-for-like. Internally: `view = build_exchange_view(context_id, tasks)` → `project_ledger(view)` → `project_collection_status(...)` → wrap in `ExchangeTurn`.

## Ordered steps

### 1. Ledger module — `bridge/src/bridge/ledger.py` (new)
Module docstring citing ADR-0003 (view, not record), A5 (deterministic sort key), `wiki/bridge-aggregate-model.md` (one doc per task), and the sense-A/B ownership split (D3). Contents:
- `LEDGER_ENTRY_KEY = "bridge_ledger_entry"` (D2).
- `stamp_ledger_entry(task: Task, entry: LedgerEntry) -> None` — `task.metadata[LEDGER_ENTRY_KEY] = entry.model_dump_json()` (D2).
- `ledger_entry_of(task: Task) -> LedgerEntry | None` — read + `LedgerEntry.model_validate_json(...)`; `None` if the key is absent (D2).
- `project_ledger(view: ExchangeView) -> list[LedgerEntry]` — fold in `view.tasks` order, skipping tasks with no entry (D4).
- `project_collection_status(view: ExchangeView, *, outstanding: Iterable[str] = (), terminal: bool = False) -> CollectionStatus` — `CollectionStatus(ledger=project_ledger(view), outstanding=list(outstanding), terminal=terminal)` (D3).
- `build_exchange_turn(context_id: str, tasks: Iterable[Task], *, outstanding: Iterable[str] = (), terminal: bool = False) -> ExchangeTurn` — builds the view internally via `build_exchange_view` and wraps the status (D5).
- `__all__` listing the above (match the M1.2 `aggregate.py` style).
- Imports: `from collections.abc import Iterable`; `from a2a.types import Task`; `from contract import CollectionStatus, ExchangeTurn, LedgerEntry`; `from bridge.aggregate import ExchangeView, build_exchange_view`. (`from __future__ import annotations` header, matching `aggregate.py`.)

### 2. Tests — `bridge/tests/test_ledger.py` (new)
Pure unit tests (no fixtures, no async — direct construction). Build test tasks with `create_leg_task(context_id=…, ordinal=n, task_id=…)` (from `aggregate`) then `stamp_ledger_entry(task, entry)`; build `LedgerEntry` objects **inline** (they're `contract` models — do not read `wiki/evals/...` and do not import `agents`). Cases:
- **Round-trip (D2):** `stamp_ledger_entry` then `ledger_entry_of` returns an equal `LedgerEntry` (compare `.model_dump()`); the JSON string coexists with the `bridge_ordinal` key in the same Struct (`ordinal_of` still works after stamping the entry).
- **`ledger_entry_of` → `None`** for a task with no stamped entry (in-flight leg).
- **Deterministic order (A5 headline):** three tasks in one context, ordinals 0/1/2, each stamped with a distinct entry; feed them to `build_exchange_turn` (or `project_ledger`) in **shuffled** input order → the resulting `ledger` is in ordinal order (0,1,2), independent of input order and of `task.id` lexical order (choose `task_id`s whose sort order contradicts the ordinal order, e.g. ordinal 0 → `t-z`, ordinal 2 → `t-a`).
- **Context filtering:** tasks from a *different* `context_id` (also stamped) are excluded from the projection (inherited from `build_exchange_view`).
- **Skip-unstamped:** a mix of stamped + unstamped tasks → the ledger contains only the stamped entries, still ordinal-ordered.
- **Container passthrough (D3):** `project_collection_status(view, outstanding=["gov-id","utility-bill"], terminal=True)` returns those exact `outstanding`/`terminal` values unchanged; default call yields `outstanding == []`, `terminal is False`.
- **Empty exchange:** no tasks → `ledger == []`, `CollectionStatus`/`ExchangeTurn` valid; `ExchangeTurn.context_id` is the passed context.
- **Shape parity:** the assembled `ExchangeTurn` validates as `contract.ExchangeTurn` and its `.model_dump(mode="json")` has the mock's key set (`context_id`, `status.ledger`, `status.outstanding`, `status.terminal`) — locks M1.13 like-for-like comparison.
