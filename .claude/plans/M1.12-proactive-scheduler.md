# M1.12 — Proactive follow-up (virtual clock)

**Milestone:** M1 — Bridge Core (local) · **Depends on:** M1.3 (skill policy), M1.2 (aggregate/context_id)
**Status:** planned

## Goal (from PLAN.md M1.12)

Durable Scheduler seam, local = in-process + **injectable virtual clock**; an SLA/policy
engine (cadence / deadline / max-nudges / escalation) read from the skill policy (M1.3);

no-duplicate guarantee rides on this (lessons **A7**).

## Design decisions (load-bearing — do not re-derive)

1. **Two-layer split, mirroring every other bridge/ module** (disposition/ledger/requirements are
   pure core; adapters/local/* is the seam impl):
   - **Pure core:** new file `bridge/src/bridge/scheduler.py` — `VirtualClock`, `Timer`, `TimerKind`,
     the SLA engine `plan_followups(...)`, and the read-model `followup_status(...)` / `FollowupState`.
     Import discipline: `contract`(if needed) + `bridge.skills` (types only, for `SlaPolicy`) +
     stdlib/pydantic. **Never** imports `agents`, `seams`, or `adapters`. Keep it OUT of
     `bridge/__init__.py` (preserve cheap `import bridge` + the no-agents guard).
   - **Adapter:** flesh out `bridge/src/bridge/adapters/local/scheduler.py::LocalScheduler` — a thin
     in-memory timer store implementing the seam over the core types. Imports from `bridge.scheduler`
     (dependency direction adapters → core).

2. **Ticks are integers.** The policy is expressed in "ticks" (`SlaPolicy` fields are `int`, C1 says
   `# ticks`). The virtual clock is an integer counter, not a datetime. This matches the frontend
   time-warp/"advance the SLA window" story and keeps everything deterministic.

3. **`Timer` is a MUTABLE model** (A7 requires marking `fired` in place). Use a **plain
   `@dataclass`** (not a frozen pydantic model) so `timer.fired = True` mutates the stored object.
   (aggregate.py already uses dataclasses; frozen pydantic — used by fulfillment/requirements —
   would block the in-place mutation A7 mandates.)

4. **Local scheduler is in-process, in-memory.** "Durable" in the task title describes the *seam
   concept*; the local adapter is an in-memory `dict[str, Timer]`. Restart-durability of the timer
   store is the **Sprint-2 GCP adapter** (Cloud Tasks; A7 "deletion is the fired signal"), NOT this
   task — M1.12 depends on M1.2/M1.3, not on Sessions durability. The durability property proven
   *here* is **exactly-once + idempotent fired-in-place**. Add a one-line comment saying the
   `Database*`/Cloud-Tasks variant lands in Sprint 2 (mirror the note in `local/exchange_store.py`).

5. **No outbound send.** `overdue → escalated` is surfaced *only* via the read-model projection
   (`followup_status`). The actual party-channel nudge send is fakeable / Phase 4
   (`wiki/bridge-proactive.md` §Egress). Do NOT add any A2A client / outbound call.

## SLA ladder semantics (C1: deadline=3, cadence=2, max_nudges=2)

`plan_followups(sla, *, start, context_id, task_id=None, id_prefix)` returns a `list[Timer]`:

- **Nudge i** for `i` in `1..max_nudges`: `fire_at = start + deadline + (i-1)*cadence`, `kind=NUDGE`,
  `sequence=i`.
- **Escalation**: `fire_at = start + deadline + max_nudges*cadence`, `kind=ESCALATION`, `sequence=0`.

For the address policy (`start=0`, deadline=3, cadence=2, max_nudges=2):
`nudge#1 @ tick 3`, `nudge#2 @ tick 5`, `escalation @ tick 7`. This is the address-demo beat 2
("Silence → overdue → reminder → escalated", `wiki/bridge-address-demo.md`). Timer ids are
`f"{id_prefix}-nudge-{i}"` / `f"{id_prefix}-escalation"`; `id_prefix` defaults to `context_id`.

2. **plan_followups (C1 policy)** — with `SlaPolicy(deadline=3, cadence=2, max_nudges=2)`, `start=0`:
   assert `fire_at`s are nudge#1@3, nudge#2@5, escalation@7; correct `kind`/`sequence`/`context_id`;
   ids `<prefix>-nudge-1/2` and `<prefix>-escalation`; `id_prefix` defaults to `context_id`.
3. **due() returns only due, sorted** — schedule the 3 timers, `due(now=5)` returns nudge#1 then
   nudge#2 (sorted by fire_at) and NOT escalation; assert deterministic order when two share a
   `fire_at` (order by sequence then id).
4. **A7 exactly-once (load-bearing)** — after `due(now=7)` returns all 3 and marks them fired, a
   SECOND `due(now=7)` (or after `advance`) returns `[]`; assert each returned timer `.fired is True`
   after the first call. This is THE test the no-duplicate guarantee rides on.
5. **cancel** — a cancelled timer never appears in `due()` even past its `fire_at`.
6. **followup_status read-model** — over a timer set: before any fire → `ON_TRACK`, `nudges_fired=0`,
   `escalated=False`; after nudge#1 fires → `OVERDUE`, `nudges_fired=1`; after escalation fires →
   `ESCALATED`, `escalated=True`. Drive it by mutating via `due()` at advancing ticks.
7. **End-to-end demo beat (ties M1.3)** — load the real policy from the address-proof skill:
   `LocalSkillRegistry().get_skill("address-proof")` → `skill.policy.sla` (or `load_skill(...)`),
   build followups via `schedule_followups`, then step the virtual clock: at tick 2 → `ON_TRACK`;
   advance to 3 and `due()` → nudge fires → `OVERDUE`; advance to 7 and `due()` → escalation fires →

   `overdue → escalated` (no outbound send). If `get_skill` is async, `await` it.
8. **schedule idempotency** — scheduling the same `timer.id` twice keeps one entry / upserts.

## Gotchas

- **A7 is the whole point.** If `due()` returns fired timers without mutating them in place, the
  exactly-once guarantee silently breaks. Mark before/at return; use a mutable `Timer` (dataclass).
- **No timestamp → deterministic sort key (A5).** Sort `due()` output by `(fire_at, sequence, id)`,
  never rely on dict order for correctness of the *returned* ordering.
- **`clock=None` must work** — the factory calls `LocalScheduler(clock=None)`; construct a default
  `VirtualClock()` inside `__init__`.
- **Keep `scheduler.py` out of `bridge/__init__.py`** and free of `agents`/`seams`/`adapters`
  imports (no-agents guard + cheap import).
- **Do NOT tighten the Protocol** — `SchedulerSeam` uses `object`/`Any` for the timer/now types on
  purpose (runtime_checkable checks method names only). Passing `Timer`/`int` at call sites is fine.
- Escalation is not a rejection and the leg holds at `escalated` (no auto-abandon) —
  `wiki/bridge-open-questions.md` "Exchange lifetime"; the read-model just surfaces the stall.
