# S0.6 — Skills scaffold + `skills-ref validate` in CI

**Sprint:** 0 (scaffolding) · **Task line:** `PLAN.md` S0.6
**Goal:** Author the demo's runtime skill folders in the **Agent Skills format** (ADR-0001, day
one) and turn the CI **skills** job — currently a placeholder — into a real gate that runs
`skills-ref validate` on every folder under `skills/`. No application code; skills are *config*.

---

## Context an executor needs (do not re-derive)

- **What a skill is here.** A skill is one Agent Skills folder (agentskills.io): a `SKILL.md` with
  YAML frontmatter (`name`, `description`, optional `license`, and a `metadata:` map) plus a Markdown
  body, optionally bundling `assets/` and `references/`. The Bridge distinguishes two *kinds* via
  `metadata.bridge-kind`: **process** (parameterizes an exchange) and **doctype** (parameterizes an
  extraction task). Full spec: `wiki/bridge-skills.md`. Demo values: `docs/lessons-learned.md §C1`.
- **Evals are NOT skills.** `wiki/evals/address/` is the grading corpus (`expected.json`, images) —
  do **not** put skills there and do **not** copy eval field-naming verbatim (see gotcha below).
  Skills live at repo-root `skills/`. This is stated explicitly in `wiki/evals/README.md`.
- **The three skills are fully specified already** in `docs/lessons-learned.md §C1`,
  `wiki/bridge-skills.md`, and `wiki/bridge-address-demo.md`: process `address-proof`, doctype
  `gov-id`, doctype `utility-bill`. Author **all three** (see "Scope" — the task line names only
  `address-proof`, but the process skill's candidate doctypes are `gov-id` + `utility-bill`, C1 gives
  their exact fields, and CI validates *every* folder under `skills/`, so ship the set).
- **`skills-ref` — resolved (S0.1 left this open on purpose).** It is the Anthropic reference library
  for Agent Skills (`github.com/anthropics/agentskills`). It ships on **both** PyPI (`skills-ref`,
  0.1.1) and npm (`skills-ref`, 0.1.5).
  - **GOTCHA:** the **PyPI** package named `skills-ref` does **not** provide a `skills-ref` executable
    — its console script is **`agentskills`**. So the docs' shorthand `skills-ref validate ./skill`
    maps to `agentskills validate ./skill` when installed from PyPI.
  - CLI verified locally: `agentskills validate SKILL_PATH` → exit **0** valid, **1** on error with a
    clear message (e.g. `Directory name 'bad' must match skill name 'wrongname'`).
  - **What it checks:** SKILL.md presence, frontmatter validity, `name` matches the directory,
    required fields. It does **not** deep-validate `assets/` contents — `policy.yaml`/`schema.json`
    schemas are a Bridge-side concern layered on later (ADR-0002), not gated here.
- **Chosen install path = uv/uvx** (the repo's Python toolchain; `astral-sh/setup-uv` is already
  pinned in `.github/workflows/ci.yml`). Pin the version: `uvx --from skills-ref==0.1.1 agentskills
  validate <dir>`. (npm alternative exists but would need a node setup in a job that otherwise needs
  none; uvx keeps the skills job single-tool.)
- **CI is already wired for this job to appear.** `.github/workflows/ci.yml` already has: a `skills`
  path filter in the `changes` job (`skills/**`), a `skills` job guarded by
  `needs.changes.outputs.skills == 'true' && hashFiles('skills/**/SKILL.md') != ''`, and `skills` in
  the `ci-success` aggregation `needs`. **Only the job body** (currently `echo "…placeholder…"` + a
  TODO comment) needs replacing. Once `skills/**/SKILL.md` exists, the `hashFiles` guard flips true
  and the job runs — so authoring the skills and wiring the job must land **together**.
- **Local validate is confirmed working** on this box (`uvx` present, uv 0.9.1). Both the process and
  doctype SKILL.md shapes below were validated → `Valid skill`.

## Design decisions (baked in — don't re-litigate)

1. **Author all three skills** (`address-proof`, `gov-id`, `utility-bill`), not just `address-proof`.
   Rationale above. Content is data/config only — no Python.
2. **Install via `uvx --from skills-ref==0.1.1 agentskills validate`**, pinned. Reuse the already-pinned
   `astral-sh/setup-uv` action; no node in this job.
3. **Frontmatter `metadata` values are strings** (the spec's `metadata` is string→string). Quote
   scalars that could be read as non-strings (`version: "1.0"`, the space-separated doctype list).
4. **Assets carry the C1 values verbatim** so Sprint 1's loaders (`ExtractionPolicy.from_mapping`,
   `SLAPolicy.from_mapping`) have real config to bind. Use the corrected key `max_resubmissions`
   (C1 flags the `max_resumissions` spelling as a `(sic)` typo).
5. **Record the local command in `skills/README.md`.** The task says "document the local command in
   the dev-env doc (S0.7)"; S0.7 isn't built yet, so drop a short `skills/README.md` now and let S0.7
   consolidate it into the root dev-env doc.

## Ordered steps

### 1. Create `skills/address-proof/` (process skill)

`skills/address-proof/SKILL.md`:

```markdown
---
name: address-proof
description: Collect proof of address for a party. Use when a servicer's agent needs address
  verification. A bounded Collect over candidate doctypes gov-id and utility-bill; the agent owns the
  completeness decision. The skill carries a prose satisfaction description (never a formal rule) the
  Bridge best-efforts an advisory assessment from.
metadata:
  bridge-kind: process
  bridge-pattern: collect
  bridge-candidate-doctypes: "gov-id utility-bill"
  bridge-policy: assets/policy.yaml
  version: "1.0"
---

Bounded Collect. The Bridge classifies each arriving doc against the candidate doctypes, dispositions
it, and chases the delta per `assets/policy.yaml`. Completeness (the OR, the count-to-two, the
distinct-issuer check) is the **agent's** — asserted per turn, never encoded here as a formal rule.
```

`skills/address-proof/assets/policy.yaml` (C1 values):

```yaml
thresholds:
  resubmit_below: 0.55
  auto_approve_at: 0.85
retry:
  max_resubmissions: 3
sla:
  deadline: 3      # ticks
  cadence: 2       # ticks between nudges
  max_nudges: 2    # ladder: overdue -> reminder -> escalated
```

### 2. Create `skills/gov-id/` (doctype skill)

`skills/gov-id/SKILL.md`:

```markdown
---
name: gov-id
description: A government-issued photo ID (driver's license, passport, national ID). Use as proof of
  identity. Extracts full name, document number, issuing authority, and expiry date; validates the
  document is unexpired and legible.
metadata:
  bridge-kind: doctype
  bridge-extraction-engine: gemini
  bridge-schema: assets/schema.json
  version: "1.0"
---

Extract the fields defined in `assets/schema.json` from the supplied ID. Validation rules live in
`assets/validation.yaml`.
```

`skills/gov-id/assets/schema.json` (C1 required fields; JSON-Schema-ish, constrained-JSON target):

```json
{
  "type": "object",
  "required": ["doctype", "full_name", "document_number", "expiry_date"],
  "properties": {
    "doctype": { "type": "string", "enum": ["gov-id"] },
    "full_name": { "type": "string" },
    "document_number": { "type": "string" },
    "issuing_authority": { "type": "string" },
    "expiry_date": { "type": "string", "format": "date" }
  }
}
```

`skills/gov-id/assets/validation.yaml` (C1: parsed, not yet enforced in Phase 1):

```yaml
rules:
  not_expired: { field: expiry_date, must_be: future }
  complete_fields: true
disposition_signals:
  legibility: true
  type_match: true
  confidence: true
  completeness: false   # sense-B is the agent's, not the Bridge's
```

### 3. Create `skills/utility-bill/` (doctype skill)

`skills/utility-bill/SKILL.md`:

```markdown
---
name: utility-bill
description: A utility bill (electricity, water, gas) from a service provider. Use as proof of address.
  Extracts and canonicalizes the issuer/company, account-holder name, service address, and statement
  date; validates the bill is recent and shows an address.
metadata:
  bridge-kind: doctype
  bridge-extraction-engine: gemini
  bridge-schema: assets/schema.json
  version: "1.0"
---

Extract the fields defined in `assets/schema.json` from the supplied bill. Canonicalize the issuer to
a stable key (`PowerCo` / `Power Co.` / `PowerCo Ltd` -> `power-co`) — see
`references/issuer-canonicalization.md`. Validation rules live in `assets/validation.yaml`.
```

`skills/utility-bill/assets/schema.json`:

```json
{
  "type": "object",
  "required": ["doctype", "issuer", "account_holder", "service_address", "statement_date"],
  "properties": {
    "doctype": { "type": "string", "enum": ["utility-bill"] },
    "issuer": { "type": "string", "description": "canonicalized issuer key, e.g. power-co" },
    "account_holder": { "type": "string" },
    "service_address": { "type": "string" },
    "statement_date": { "type": "string", "format": "date" }
  }
}
```

`skills/utility-bill/assets/validation.yaml`:

```yaml
rules:
  recent_bill: { field: statement_date, window_days: 90 }
  address_present: { field: service_address }
disposition_signals:
  legibility: true
  type_match: true
  confidence: true
  completeness: false
```

`skills/utility-bill/references/issuer-canonicalization.md` — short prose of the rule (honor the
invariant): strip only corporate suffixes `Ltd / Inc / LLC / GmbH / …`; **"Co." is NOT a suffix** —
`"Power Co."` → `power-co`. Lowercase, hyphenate. (Cross-ref `docs/lessons-learned.md` A4.)

### 5. Replace the CI `skills` job body in `.github/workflows/ci.yml`

Swap the placeholder `echo` step (and its `TODO(S0.6)` comment) for a real validate loop. Keep the
job's `needs`/`if` guard and the pinned `actions/checkout` SHA already in the file. New body:

```yaml
  skills:
    needs: changes
    if: needs.changes.outputs.skills == 'true' && hashFiles('skills/**/SKILL.md') != ''
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@eef61447b9ff4aafe5dcd4e0bbf5d482be7e7871   # v4.2.1
      - uses: astral-sh/setup-uv@0d1b58c5f02339bd2e8b5c16ba38a44ed8672d95   # v6.0.0
      - name: Validate Agent Skills folders
        run: |
          status=0
          for d in skills/*/; do
            [ -f "${d}SKILL.md" ] || continue
            echo "== validating ${d}"
            uvx --from skills-ref==0.1.1 agentskills validate "$d" || status=1
          done
          exit $status
```

Notes: run from repo root (no `working-directory`); the loop validates **all** folders and fails if
**any** fails (don't short-circuit on the first — report them all). `${d}` includes a trailing slash
(`skills/address-proof/`), so `${d}SKILL.md` is correct.

## Seams touched

**Skill registry seam — format only, no adapter.** S0.6 lays the on-disk Agent Skills folders that
are the **seam contract itself**: `wiki/bridge-seams.md` states both adapters store the identical unit
(a skill folder), the local adapter is a *directory* of these folders and the GCP adapter is the
managed Skill Registry holding the same folders, and `skills-ref validate` gates both. So authoring
the format-correct folders here is exactly what makes the future local↔GCP swap a no-op. **No adapter
code and no local/GCP impl is built in S0.6** — that's Sprint 1/2. No `@pytest.mark.seam` test is
added here (the seam harness, S0.3, is for runtime adapters; skill validation is a CI shell gate).

## Tests to add

## Gotchas recap

- **PyPI `skills-ref` → `agentskills` executable**, not `skills-ref`. Use
  `uvx --from skills-ref==0.1.1 agentskills validate`. Do not `uvx skills-ref …` (no such script).
- **Directory name must equal frontmatter `name`** — `agentskills validate` fails hard otherwise.
- **Skills ≠ evals.** Author under repo-root `skills/`, never `wiki/evals/`.
- **Field-naming divergence (flag, don't fix here):** `wiki/evals/address/expected.json` uses
  `key_fields` names (`name`, `doc_number`, `issuing_authority`, `expiry`) while C1 specifies the
  skill schema fields (`full_name`, `document_number`, `issuing_authority`, `expiry_date`). Follow
  **C1** for the skill `schema.json` (it's the authoritative config record; extraction isn't wired
  until Sprint 1). Reconciling eval↔schema naming is a Sprint-1 concern — leave a note, don't force it.
- **`max_resubmissions`**, not `max_resumissions` (C1's `(sic)`).
- **Authoring skills and wiring the CI job must land together** — the job's `hashFiles` guard means it
  stays skipped (and green) until the first `SKILL.md` exists.
- **Validate loop must not short-circuit** — collect a non-zero status across all folders so one bad
  skill doesn't mask others.
